# 本机 API 测速与 Maplewood 示例对照

2026-10-08 按用户明确授权，在 Windows 本机使用已保存的 API 和 Key 直接发 HTTP
请求。没有在本地编译 App、运行 Gradle、启动模拟器或 Agent。LLM 仍是
`gpt-5.6-luna`，TTS 仍是 `mimo-v2.5-tts`、白桦音色。凭据、生成文本和音频不写入报告。

## 本机实测

所有延迟都从发请求开始，到第一段实际文字或第一块可用音频，不把响应头或空 SSE
事件当成生成结果。未推断本机出口的地理位置。

| 对照 | 首段可用内容 | HTTP |
| --- | ---: | --- |
| LLM 第一条简单问候 | 5.685s | 200 |
| LLM 后续两条简单问候 | 2.415 / 2.422s | 200 |
| LLM 与 Agent 相同的指令、开场白及测试问题 | 2.868 / 2.245s | 200 |
| LLM 后续连续请求 | 无生成 | 三次 429；Retry-After 9 / 8 / 7s |
| LLM 冷却后 Chat | 3.245s | 200 |
| LLM 冷却后 Responses（同样的对话输入） | 3.772s | 200 |
| 小米流式 TTS，同一中英文句子 | 1.241 / 0.787 / 0.752s | 全部 200，13–15 个音频块 |
| 小米完整 WAV，同一中英文句子 | 1.988 / 1.684s | 全部 200 |
| 小米三路并发短句 | 1.131 / 0.912 / 0.778s | 全部 200 |
| 小米并发后再请求短句 | 1.071s | 200 |

小米共 10 个请求（包含预热和并发）都为 200，没有观察到 429。此次明确的限流响应
来自 LLM 中转，冷却后恢复成功。不能凭 429 推断中转具体 RPM/TPM 额度，也不能推断
此前每次慢回复都由限流导致。

这次本机 TTS 首块比此前 Cloud 会话 1.55–1.89s 更快，说明端到端路由及测试环境值得
考虑。两个环境不是同一时刻、同一客户端和全部相同文本，不能把差值完全归因于地理位置。
LLM 本机也没有复现亚秒首字；“当前中转调用链存在等待”比“模型本身慢”更准确。

小米[官方限流说明](https://mimo.mi.com/docs/zh-CN/api)列出 `mimo-v2.5-tts` 默认
100 RPM、10M TPM，按账号同模型下所有 Key 汇总，并说明并发或服务负载可能引起
延迟或 429。这不等于已测到此账号被限流，少量请求也不能证明长期不会限流。

## Maplewood 公开实现

已找到这个按钮对应的[官方患者接待配方](https://docs.livekit.io/reference/recipes/spacexai-patient-intake/)，
它仍是 STT → LLM → TTS 三段流水线，公开配置为：

| 环节 | Maplewood 配方 | 当前 Agent |
| --- | --- | --- |
| STT | LiveKit Inference `xai/stt-1`，英语 | 外部 Deepgram Nova-3，中文和英语双路 |
| LLM | Inference `xai/grok-4.3`，reasoning_effort=none | 外部中转 `gpt-5.6-luna`，SDK 同样默认 none |
| TTS | Inference `xai/tts-1`，carina | 外部小米 `mimo-v2.5-tts`，白桦，流式 PCM |
| 断句 | Inference TurnDetector，动态等待 1.2–4.0s | Silero VAD，固定等待 0.45–1.5s |
| 答复风格 | 短答，一次问一个问题 | 短答，一至两句，指令上限 80 个汉字 |

官方[集成概览](https://docs.livekit.io/agents/integrations/spacexai/)给的通用 LLM
配置为 `xai/grok-4.20-0309-non-reasoning`，与患者接待配方的 `xai/grok-4.3` 不同；
上表依据患者接待专门配方，不声称已经读取按钮线上当前部署的私有配置。

LiveKit 将 Inference 描述为降低延迟的接入方式。模型、提供商和接入路径与当前方案
有差别，但不据此断言所有模型在同一台机器或同一机房。官方示例的静默等待下限还高于
当前设置，不能把它的速度简单归结为把静默时间设得更短。

推断：模型及推理接入路径更值得比较。此次没有测官方示例的分段指标，不能量化每个
差异的收益，也不保证照搬其设置就能得到相同速度。其英语演示不能替代中英混合验收。

下一步优先查清 LLM 中转的 429 规则，并控制 Agent 预生成或重试带来的重复请求；
保留模型的前提下，再做相同请求内容与频率的路线对照。此次只进行本机测量和资料分析，
没有替换模型、修改 App 设置或再次部署后端。
